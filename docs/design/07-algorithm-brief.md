# 后台算法交接方案

写给负责后台算法的设计者。界面、交互、EQ 预设库和开箱默认值由维护者直接改并发布，本文只收需要你来设计和构造的部分：设备真实在线判断、无感切换、响度与柔着陆、麦克风诊断，以及 EQ 推荐怎样真正生效。

每一节按同一顺序写：代码现在怎么做、哪里不够、目标与可测指标、建议方案、与现有代码的接口、怎么验证。现状以 v1.4.0 源码为准，没有实机数据的地方直接写未测。

## 0. 先说结论

后台部分的反馈，根因可以归为三类。

1. **在线信号只有一个。** `AudioCore.List` 只保留 `DEVICE_STATE_ACTIVE` 的端点，`JackSense` 只对板载声卡读插孔。USB 无线接收器和一直在线的声卡，耳机关机或线缆拔出后是否上报，取决于驱动，本机诊断文档也写明了这一点。程序没有第二个证据去核对 Windows 的说法。
2. **决策是手调的整数规则。** `RouteCandidate.Score` 把偏好、新近度、声道、场景适配加减成一个整数，权重写死，门槛只靠一根滑杆。设计文档里写的偏好模型（上下文 Bandit）没有实现。
3. **调优缺少听感输入。** 等响匹配用的是端点增益的 dB 差，不是响度。麦克风诊断只用分块能量、削波计数、50/60 Hz 分量和播放电平包络，没有频谱，也没有语音检测。EQ 只是按型号名查表，没有任何地方真正应用。

另有两处属于体验默认值，由我改，不在本文范围：智能切换和自动调音原先都默认关闭，用户开箱看不到任何自动行为。b632944 起全新安装默认开启，从旧版升级的保持原来的开关；设备页的提示文字和术语已整理。

建议的验收指标如下，请在方案里确认或修改。

| 指标 | 现状 | 建议目标 |
| --- | --- | --- |
| 日常列表中误判在线的设备占比 | 未测 | 低于 2% |
| 从事件到默认设备切换完成，中位数 | 模拟端点 429 ms，实机未测 | 低于 500 ms，并给出实机分布 |
| 稳定期自动动作被撤销的比例 | 未测 | 低于 5% |
| 通话中的误切换 | 模拟下为 0 | 实机为 0 |
| 切换前后同一内容的响度差 | 未测 | 不超过 2 LU |
| 麦克风诊断与人工判断一致率 | 未测 | 不低于 90%，削波零漏检 |

## 1. 设备真实在线判断

**现在怎么做。** 判断设备是否在线，程序只用三样东西。

- `AudioCore.List` 只枚举 `DEVICE_STATE_ACTIVE` 的端点，已拔出、已禁用、不存在的一律当作没有。
- `JackSense` 通过拓扑接口读 3.5 mm 插孔的连接位，只对板载声卡读（`AudioDiscovery.Describe` 里限定了板载音频，且形态不是数字口）。
- `PlugChanges` 和 `OutputArrivals` 在本次运行内记下新出现的端点 ID，当作「刚接入」。程序重启后这份记忆归零。

**哪里不够。**

1. 一直在线的端点没有第二证据。USB 无线接收器、外置声卡、蓝牙耳机的立体声端点，耳机关机后 Windows 是否把端点置为非活动，取决于驱动。本机诊断文档已经记下这一点，面板对此无能为力。
2. 「在线」不等于「在用」。端点活动但耳机没开机、没戴上，程序仍把它当候选，自动切过去就是无声。这很可能是「不能有效识别真正接入的设备」的主要来源，但没有实机数据，未验证。
3. 证据没有强弱。`AudioPanel.Apply` 里是有就是有的布尔判断，`SwitchEvidence` 里也看不到在线证据有多强。
4. 没有设备自己的可靠性档案。某个设备总是在线、总被用户切走，这类行为只进了 `RouteTrust` 的偏好分，没有回到在线判断。

**目标。** 对每个物理设备组输出存在度，而不是布尔值。

| 状态 | 含义 | 自动切换允许的最高自治 |
| --- | --- | --- |
| 确认在线 | 至少两条独立证据，或一条强证据 | 按用户设定 |
| 可能在线 | 只有 Windows 端点状态，没有佐证 | 只提示或一键执行 |
| 不明 | 证据互相矛盾，或设备属于一直在线类 | 不自动切换 |
| 已离线 | 强证据表明已断开 | 不参与候选 |

**建议方案。**

1. 证据来源只用现有官方接口，不读取音频内容：端点状态与通知时序；KS 插孔位，若 USB 驱动提供同样的拓扑则一并读取；PnP 节点状态和 `ContainerID` 是否存在（`AudioDiscovery` 已在用 cfgmgr32）；蓝牙连接状态（容器层的连接属性，哪些属性在哪些驱动上有效需要实测）；会话与峰值（有进程在向该端点播放且峰值非零，可证明在用，静音不能证明离线）；用户行为（刚手动选择、刚撤销自动切换）。
2. 融合用规则，不要一上来就上学习模型。每个组维护一个小状态机，带迟滞，沿用 400 ms 去抖和 `SceneTracker` 的驻留思路。证据分强、弱、矛盾三类，冷启动必须可解释。
3. 学习设备类别。对 Windows 总说在线的设备，统计它被自动切换后 30 秒内被用户切走的次数，累计到阈值就标为一直在线类，降级为只提示。`DecisionJournal` 里已有 `corrected` 和 `undone` 记录，不需要新增采集。
4. 不主动对用户设备开流探测。需要采样时只能由用户在调优页发起，沿用 `TuningStream` 的约束。

**接口。** 新增纯逻辑类 `DevicePresence`，不碰 Windows。输入一次扫描的 `SmartGroup` 列表、上次状态和证据快照，输出每组的状态与理由列表。`AudioPanel.Apply` 用它替换 `plugs.Recent` 和 `physical` 过滤，`SmartPolicy.IsPrimary` 与 `AudioPanel.Eligible` 读它的结果。理由写进 `SwitchEvidence`，让决策回放可以复现。界面侧我会在设备卡片上预留状态点和一句人话理由，等你的类型定下来再接。

**怎么验证。** 把证据序列化成固定样本，放进 `tests/PresenceTest.cs` 回放：USB 无线接收器关机、蓝牙耳机断开但端点残留、板载口拔插、驱动重启造成的状态抖动、程序重启后的冷启动。新增源文件要同时加进 `Build.ps1` 和 `tests/Run.ps1`。编译器只支持 C# 5，不要用 `?.` 和字符串插值。实机验收按设备类型记录误判次数和判定耗时。

## 2. 无感切换

**现在怎么做。** 一次自动切换的链路是：端点通知进入 `AudioEventBus`，`ScanGate` 合并 400 ms 内的突发（最长等 2 s），后台全量 `AudioDiscovery.Scan`，`SceneContext.Read` 读场景信号，`PlanRoute` 给候选打分，`ExecuteRoute` 写三个默认角色并读回。

总分 = 偏好（-24 到 24）+ 新近度 36 + 立体声 5 + 从蓝牙免提恢复 30 + 场景适配 22 或 12 - 切换代价（每个活动会话 2 分，最多 20）。新候选要领先当前输出 `4 + (100 - 积极度) / 4` 分才切。切换或手动操作后静默 30 秒，场景变化要持续 5 秒、上一场景驻留 15 秒才确认。

**哪里不够。**

1. **最先要核实的一条：共用端口护栏很可能挡掉了大部分自动切换。** DeskAudio 自己切换时把三个角色写成同一个端点（`Three`），之后默认通信端点就等于默认播放端点。`SceneContext.Read` 对通信端点上每个活动会话调用 `Category`，进程不在那份约 25 个名字的白名单里就返回 null，而判断 `kind != 音乐、影音、游戏` 对 null 也成立，于是 `SharedBusy` 为真，`Guard()` 返回「通信与媒体共用端口，无法确认当前会话用途」，整次切换被记为 skipped。换句话说，只要浏览器、微信这类未登记的应用正在出声，新设备接入就不会自动切。这是读源码的推断：离线回放的信号是固定值，没有走到这条路径，实机未验证。验证办法很便宜，统计 `decisions.json` 里 skipped 记录的原因分布。
2. 场景识别靠进程名白名单和前台窗口，浏览器里的会议、视频、游戏看不见。摄像头判断依赖注册表里的最近使用时间戳。
3. 延迟预算没有实测。维护记录里的 429 至 459 ms 来自模拟端点，其中 400 ms 是去抖，不含真实 `Scan` 的耗时。每次扫描都全量读两个方向的端点、注册表、cfgmgr32 和插孔拓扑。
4. 切换瞬间应用音频流会被 Windows 重建，间隙长度未测。现在只有目标端点音量淡入，没有交叉淡化。自己指定了输出设备的应用不跟随默认设备。真正无缝要靠自有虚拟设备或每应用路由，两者都在 P5，受驱动签名和未公开接口约束。
5. 权重是写死的整数。设计文档里的偏好模型（上下文 Bandit）没有实现，`RouteTrust` 只做加减。

**目标。** 在通话误切仍为 0 的前提下，提高「该切时确实切了」的比例；每次 skipped 都能用一句人话说清原因。具体数字等第 1 条验证后再定，不先拍脑袋。

**建议方案。**

1. **先测量，再改决策。** 给 `DecisionRecord` 增加分段时间戳（通知、去抖结束、扫描完成、决策完成、写入完成、读回完成）和结构化的 skipped 原因码。时间线因此能回答「为什么没切」，延迟分布也有了真实来源。
2. **拆开共用端口护栏。** `SharedBusy` 的本意是分不清通话和媒体。应改用更强的证据，例如同一进程是否同时占用录音会话、摄像头占用、已知通话应用的可执行文件匹配，而不是用白名单反推。会话层还能提供哪些可靠信号，需要在实机上调研。证据不足时降级为 L1 一键执行，不要整体阻断。
3. **增量扫描。** 端点事件带着端点 ID，只重新描述发生变化的端点，其余沿用缓存，把扫描耗时降到可以忽略。`EndpointCache` 的复用思路可以参考。
4. **决策模型。** 硬约束保持不变。评分改成可校准的概率，先验取当前权重的等价值，使新旧模型在回放语料上结论一致，再逐步引入用户纠正作为反馈。每个候选必须仍能给出分项解释。
5. **间隙问题先实测。** 在真实 USB 耳机和蓝牙耳机上记录切换前后播放流的中断时长，数据出来之前，界面和文档都不使用「无缝」这个词。

**接口。** 护栏与证据收集集中到 `SceneContext` 和新的 `SwitchGuard` 纯逻辑类，输入信号快照、输出放行或阻断加原因码。`PlanRoute` 只读它的结论。离线回放新增「未登记应用出声时接入新耳机」「同时占用录音与播放」两类样本。

**怎么验证。** 先在 `tests/SceneSwitchTest.cs` 补一个会重现第 1 条的失败用例，再改实现。实机验收按设备类型记录：自动切换成功率、skipped 原因分布、撤销率、切换耗时分段。

## 3. 响度匹配与柔着陆

**现在怎么做。**

- `AudioCore.GainPoints` 读端点的音量范围和当前位置的 dB 值。`VolumeTuning` 为每台设备保留最近 16 次舒适音量，连同当时的 dB 一起存成「百分比@dB」。
- `AudioPanel.MatchedLevel` 在两端都有 dB 锚点时，取各自的中位锚点，按「目标舒适 dB + (源当前 dB - 源舒适 dB)」算出目标 dB，再用 `Landing.FromDb` 在三点曲线（最小、当前、最大）上线性插值回百分比。缺 dB 信息时退回 `Landing.Plan` 的百分位偏移。
- 耳机类端口冷启动上限 35%，有历史后取第 85 百分位，最高 60%。起始音量取 `min(原值, min(12, 目标 / 3))`，每 140 ms 一步：扬声器 6 步（约 0.84 s），耳机最多 18 步（约 2.5 s）。淡入期间 `AudioCore.Peak` 达到 0.94 就降音量并停止。
- 舒适点有两个来源：用户在调优页点「记住当前音量」；启用后，面板里稳定 3 秒的音量变化（滑杆操作为 1.5 秒）也会被记下。

**哪里不够。**

1. **匹配的是端点增益，不是听到的响度。** 端点 dB 不含耳机灵敏度、阻抗、驱动器增益和内容响度。两台设备「相对 dB 相同」不等于耳边一样响。设计文档和 README 已承认这一点，但第 0 节写的「不超过 2 LU」需要先定义在哪里量，见下面的目标。
2. **舒适点被内容污染。** 自动学习不看当时播的是什么，大动态的影片和压得很满的流行乐会把同一台设备的舒适点拉向不同位置。16 条原始样本不分场景，夜间和白天的舒适点也没有分开。
3. **峰值保护的信号弱。** `Peak` 是瞬时峰值，0.94 接近满幅，只能拦住快要削波的情况，拦不住「持续很响但没削波」。源码也没有说明这个峰值取在端点音量之前还是之后，我没有验证；如果取在之前，降低端点音量就不会让读数下降，保护逻辑的表现需要实测确认。
4. **增益曲线只有三个点。** 真实的 dB 对百分比曲线在不少驱动上是分段的，线性插值的误差没有测过。
5. **淡入在百分比域线性爬升。** 它在 dB 上是否均匀、听感上起步几步是否过大，没有测过，建议按 dB 规划。
6. **听力保护的上限是百分比。** 同样的 60%，在不同设备上的实际输出差别很大。

**目标。** 每台设备有一个舒适点（端点 dB，并按内容响度归一）和一个以 dB 表示的硬上限。切换后首次可闻响度与舒适点的偏差可以测量。

指标要分两层定义，先请你确认。

| 层 | 测量点 | 现有条件 |
| --- | --- | --- |
| 端点内 | DeskAudio 自己播放的参考音，用 WASAPI 环回在端点内量短时响度 | 可在 `TuningStream` 现有机制上做，需先确认环回取点相对端点音量的位置 |
| 耳边 | 测量话筒加耦合腔，或固定听音小组 | 仓库里没有这套条件，未测 |

**建议方案。**

1. 规划全部放在 dB 域：舒适点存端点 dB，硬上限存 dB，淡入按 dB 步进。百分比只在写入端点时转换。
2. 加一个可选的内容响度估计：环回采集系统混音，做 K 加权的短时响度（ITU-R BS.1770 的做法），只在内存里保留标量，不保存样本，沿用 `TuningStream` 的约束：用户开启，通话和录音期间不采。它有两个用途：把自动学到的舒适点归一成「内容响度为参考值时的端点 dB」；在淡入期间判断是否持续偏响，取代瞬时峰值。能不能用，取决于环回取点是否在端点音量之前，必须先在真实设备上确认。
3. 舒适点估计按（设备，日间或夜间）分开，样本带时间衰减，用稳健估计丢掉离群值。样本太少时规划器返回保守默认值，并把「样本不足」写进理由。样本数阈值由你定。
4. 增益曲线多取几个点，用单调插值。发现曲线不单调或读回不一致时降级为百分比域，并在理由里写明。
5. 柔着陆只由规划器给出起始 dB、步长、时间常数和上限，规划器自己不写音量。`VolumeTuning.Begin`、`Step`、`Restore` 的所有权、读回校验和跨实例保护保持原样，那是 v1.4 已验收的部分。
6. 安全不变量不变：冷启动不抬高音量；会议、录音、静音、用户手动改音量时立即停止淡入；耳机类上限从保守值起步，用户可以调。

**接口。** 新增纯逻辑类 `LevelPlanner`。输入：源和目标端点的 `GainPoint[]`、两侧历史、场景、是否耳机类、可选的内容响度。输出：起始百分比、目标百分比、步进表、上限和理由文本。它替换 `Landing.Plan`、`Landing.FromDb`、`Landing.Ceiling` 和 `MatchedLevel` 里的计算，`PrepareLanding` 与 `AdvanceLanding` 只读它的结果。`Comfort/` 的存储格式要加版本号，旧记录保持可读。

**怎么验证。** `tests/TuningTest.cs` 里现有的 `Landing` 用例是迁移基线：新规划器在这些用例上要给出相同或更保守的结果。再补几类样本：曲线不单调，驱动只暴露两个点，舒适点里有离群值，日夜样本混合，内容很响但没有削波。实机验收需要测量话筒，在固定参考音上量端点 dB 和耳边响度差，按设备类型记录。

## 4. 麦克风诊断

**现在怎么做。** `TuningStream.Diagnose` 在所选录音端口开 16 kHz 单声道共享模式流，每 50 ms 一块，共 100 块（5 秒）：前 30 块是安静段，后 70 块是说话段。`MicAnalysis` 只保留每块 RMS、全程峰值、满幅样本数、安静段 50/60 Hz 的累积能量，以及同步读到的默认输出峰值。判定规则如下。

- 说话电平取说话段 70 块 RMS 排序后的第 56 个（约第 80 百分位），安静电平取安静段总能量。
- 几乎无输入：峰值低于 -70 dBFS。偏低：说话电平低于 -32 dBFS。底噪高：安静电平高于 -42 dBFS。削波：满幅样本（≥0.995）不少于 3 个。
- 嗡声：安静电平高于 -65 dBFS，且 50 或 60 Hz 分量占安静段能量的比例超过 0.38。
- 回声风险：播放包络与话筒包络在 0 到 250 ms 延迟内的相关系数大于 0.82，且播放电平变化足够。
- 一键调整：削波降 10 个百分点；仅偏低、信噪比不小于 8 dB、无其他异常时升 8 个百分点。

**哪里不够。**

1. 没有语音检测，全靠提示语。安静段里有人说话会抬高底噪读数，说话段没出声会被判成偏低，两者现在分不开。
2. 没有频谱。看不到低频隆隆声、高频嘶声、嗡声谐波，也认不出带宽受限的话筒（蓝牙免提的窄带就是这一类）。16 kHz 采样最多只能看到 8 kHz。
3. 增益建议是固定的百分点，不是 dB，也没有用 `GainPoints`。同样的 8 个百分点在不同设备上相差几个 dB，调整后也不会自动复测。
4. 全部阈值是手调的，没有用真实语音校准，准确率未测。
5. 回声只看包络相关，播放电平不变就无法评估；参考电平来自 `PeakMeter` 轮询，对齐精度受 50 ms 块限制。
6. 读数里是否含端点增益，取决于驱动和音频引擎的处理位置，我没有验证。这决定「调输入音量」能否让读数按预期移动，需要先在实机上量一次。

**目标。**

| 指标 | 现状 | 建议目标 |
| --- | --- | --- |
| 与人工判断一致率 | 未测 | 不低于 90% |
| 削波漏检 | 未测 | 0 |
| 一次调整后说话电平进入目标区间的比例 | 未测 | 请你定区间和比例 |
| 安静段有人说话时的误判 | 未测 | 不报「底噪高」，改提示重测 |

**建议方案。**

1. 轻量语音检测：用短时能量、过零率和自适应阈值，不上模型。三个用途：说话段没有语音时提示「没听到说话」；安静段混入语音时丢弃该块并顺延；说话电平改取语音块的稳健分位。
2. 频谱摘要：每块只累加约 24 个频带的能量，不保留样本。由此区分嗡声及谐波、低频隆隆声、高频嘶声和带宽受限。要看 8 kHz 以上需提高采样率，由你定取舍。
3. 增益建议改成 dB：用说话电平与目标区间的差，经 `GainPoints` 换算成百分点，单次步长设上限，写入后回读并提示复测。削波按峰值余量算。
4. 回声：可选用环回取播放混音的包络，对齐更准，也能给出延迟估计。仍只存包络，沿用 `TuningStream` 的约束：用户发起，通话和录音期间不采，不保存音频。
5. 每项结论带置信度和一句人话，互相冲突时降级，例如嗡声与底噪高同时成立时先报嗡声。

**接口。** `MicAnalysis.Add` 和 `Finish` 的签名不变，频谱与语音检测在内部累积，`MicReport` 增加字段并保持旧字段可读。把 `GainChange` 换成 dB 目标，由新的纯逻辑类 `MicAdvisor` 输出；`AudioPanel.ApplyMicFix` 只读它的结果，仍走 `levels.Begin` 事务和读回校验。新增源文件要同时加进 `Build.ps1` 和 `tests/Run.ps1`。

**怎么验证。** `tests/TuningTest.cs` 里现有的 `Analyze` 合成用例是迁移基线，新分析在这些用例上结论要一致。再补：带谐波的嗡声、低频隆隆、高频嘶声、4 kHz 截止的窄带语音、安静段有人说话、说话段没出声、削波发生在说话中途、播放音量恒定。人工标注语料放在 `local/`，不进仓库，只提交特征序列。实机验收按设备类型记录与人工判断的一致率。

## 5. EQ 推荐怎样生效

**现在怎么做。**

- `EqPreset.Load` 读入 734 款预设，每款含前级增益和 10 段滤波。滤波类型只支持 PK、LSC、HSC，其余类型 `Band` 会直接抛错。`Preamp` 和 `Rows` 已公开，供界面显示。
- 型号识别：`MatchPreset` 先取该设备保存的选择（`EqModel/` 加设备键），没有就调用 `EqPreset.Match`，传入设备名、端口名和总线名。`Match` 把名字里的 headphones、stereo、bluetooth、耳机、立体声等词去掉并折叠标点，要求结果与型号名（或去掉品牌的型号名）完全相等，且恰好命中一款，否则返回空。
- 生效：没有任何一处把 EQ 作用到系统声音。A/B 试听由 `TuningStream.Audition` 在所选端口播放 2 秒合成音，EQ 版本用 RBJ 双二阶在 DeskAudio 自己的样本上滤波，A 和 B 对齐到同一 RMS。导出是 Equalizer APO 格式的文本，由用户自己加载。设计文档 03 也写明，没有处理链之前只给推荐和导出。

**哪里不够。**

1. 推荐只在用户打开调优页并选中端口后才出现。耳机接入时没有任何提示，设备页也没有「这副耳机有可用 EQ」的入口。
2. 识别的精度高、召回低，这是读规则得出的判断，召回率未测。完全相等的规则不会把 HD 6000 误配成 HD 600，但蓝牙名字常带厂商前缀或型号后缀，这类会落空。USB DAC、声卡和插在板载口的有线耳机，Windows 名字里根本没有耳机型号，只能靠用户选择。选择绑在设备键上，用户换一副耳机后会沿用旧型号，程序无从知道。
3. 同一型号只有一份测量，来自一台样品。入耳式受佩戴和耳道密封影响更大。个体差异、耳垫老化和二手机都不在数据里。目录给的是 AutoEq 固定提交的默认结果，用户没有强度、低频量感、高频亮度可调。该提交用的目标曲线我没有核对。
4. A/B 对齐的是 RMS，不代表真实应用后的响度，也没有头部空间检查。前级增益是目录给定的，叠加其他均衡器或 Windows 增强后会不会削波，没有人验证。
5. 因为没有生效路径，还原、通话和录音期间暂停、与用户已有的 APO 配置共存这些要求也都没有实现。

**目标。** 先把「生效」分成三档，请你确认做到哪一档。

| 档 | 含义 | 依赖与约束 |
| --- | --- | --- |
| 0 | 推荐加导出（现状） | 无 |
| 1 | 向 Equalizer APO 写配置，可一键还原 | 用户已安装 APO。安装和端点注册通常需要管理员权限，由 APO 自己的安装器完成。热加载行为和覆盖的端点范围未测 |
| 2 | 自有处理链（自有 APO 或虚拟设备） | 驱动签名，属于 P5，本文不设计 |

指标如下，请确认或修改。

| 指标 | 现状 | 建议目标 |
| --- | --- | --- |
| 型号误配率（把错误的型号当成对的） | 未测 | 低于 1%，宁可不推荐 |
| 带常见前后缀的设备名识别召回率 | 未测 | 请你定 |
| 无法确定时是否交给用户确认 | 否 | 是，且不自动应用 |
| 应用后的频响与理想滤波器偏差，20 Hz 到 20 kHz | 未测 | 不超过 0.1 dB |
| 满幅输入下应用后削波 | 未测 | 0 |
| 还原后配置与应用前一致 | 无 | 逐字节一致 |

**建议方案。**

1. **识别改成带置信度的候选排序。** 输入设备名、端口名、总线、品牌词和用户历史选择，输出前几名候选、分数和理由。只有一个高置信候选才允许自动应用，其余只提示，由用户确认。名字别名表（品牌前缀、LE_ 之类的传输前缀、地区型号后缀）放在数据文件里，不写死在代码中。用户的纠正写回设备档案，并且绑定到端点和插孔，不只绑设备键，避免换耳机后沿用旧型号。
2. **强度可调。** 提供 0 到 100% 的强度，对各段增益等比缩放，Q 和中心频率不变。前级增益按缩放后的总频响重新计算，取 20 Hz 到 20 kHz 内的最大正增益再留余量，不沿用目录值。强度 100% 时结果要与目录前级一致。是否再加低频和高频两个偏好旋钮，由你定。
3. **档 1 桥接。** 检测 APO 是否安装，只写 DeskAudio 自己的独立配置文件，再在主配置里加一行 Include 引用，不覆盖用户原有内容。写之前备份主配置并记下哈希，还原时对比哈希，被外部改过就停下来提示，不强行覆盖。文件路径和 Include 语法需要对照 APO 文档核对。APO 是第三方程序，它的许可和分发条件需要你确认。DeskAudio 不内置、不分发，只检测并写配置。独占模式的应用不经过系统效果，这类应用拿不到 EQ，界面要写明。
4. **效果自检。** 用 DeskAudio 自己的参考音在所选端口播放，同时用环回取样，对比应用前后的频谱差。环回取点相对系统效果的位置未知，和第 3 节是同一个问题，建议合成一次实机调研。如果取点在效果之前，自检就看不到 EQ，只能改用测量话筒，那样仓库里要补测量条件。
5. **安全不变量。** 应用前先给出头部空间结论。通话和录音期间不改处理链。所有改动可一键还原，并写入活动时间线，沿用 `tuned` 记录类型。APO 被卸载或配置丢失时回到「未应用」状态，不报错。

**接口。** 新增三个类，前两个是纯逻辑，不碰 Windows。`EqMatcher` 负责名字到候选及置信度。`EqPlanner` 输入 `EqPreset.Rows`、`Preamp`、强度和采样率，输出滤波参数、前级增益、头部空间和警告文字。`ApoBridge` 只做文件读写，通过接口注入，测试用临时目录里的假配置替身。`EqPreset.Match` 保留为 `EqMatcher` 的薄封装。设置里沿用 `EqModel/<设备键>`，新增 `EqStrength/<设备键>` 和 `EqApplied/<端点>`，设置文件版本仍为 1，只增键。界面侧我会加「应用」开关、强度滑杆和状态点，等你的类型定下来再接。新增源文件要同时加进 `Build.ps1` 和 `tests/Run.ps1`，编译器只支持 C# 5。

**怎么验证。** `tests/TuningTest.cs` 里现有的 EQ 用例是迁移基线：measured model match、model number boundary、unknown stays unmatched、A/B uses actual filter、bounded audition、complete measured catalog with attribution，新实现必须保持通过。再补以下几类。

- `EqMatcher`：用目录里的型号名加上常见前后缀生成语料，统计召回，同时保证「USB DAC」「HD 6000 USB」这类名字不被误配。
- `EqPlanner`：强度 100% 时前级与目录一致，误差不超过 0.1 dB。强度 0% 时频响平直。任意强度下满幅输入不削波。频响用独立实现的公式计算，不复用 `Band`，与它交叉校验。对全部 734 款跑一遍，列出最大增益和最大 Q 的预设，供你定上限。
- `ApoBridge`：写入后原有配置内容保留，还原后逐字节一致，被外部改过时拒绝覆盖，APO 不存在时退回「未应用」。
- 实机验收：在装有 APO 的机器上记录配置热加载耗时、覆盖的端点范围、独占模式应用的表现，并按设备类型记录自检频谱差。

## 6. 交付顺序与验收

**顺序的理由。** 第 2 节第 1 条是整份方案里最便宜、也最可能改变优先级的核实，放在最前。第 1、2 节共用一份「谁在出声、为什么没切」的数据，所以先做决策记录的原因码和分段耗时。第 3 节和第 5 节有同一个未知量：环回取点相对端点音量和系统效果的位置，合并成一次实机调研。第 4 节和 EQ 档 1 彼此独立，可以并行。

全新安装现在默认开启智能切换和自动调音（b632944），升级用户保持原开关。所以第 2 节第 1 条和第 3 节的保护不再只影响主动打开它们的人，新用户开箱就会遇到，这是把第 0 到 2 步放前面的另一个理由。自适应自治级别仍从 L2 起步，会议、录制、离开和占用不明仍然阻止自动动作，这些护栏我没有改。

**建议顺序。**

| 步 | 内容 | 依赖 | 产出 |
| --- | --- | --- | --- |
| 0 | 实机核实：统计 `decisions.json` 里 skipped 的原因分布；同机量一次环回取点位置 | 无代码改动 | 一页记录，决定第 2、3、5 节的优先级 |
| 1 | `DecisionRecord` 分段时间戳和结构化原因码（2.1） | 无 | 时间线能回答「为什么没切」，延迟分布有真实来源 |
